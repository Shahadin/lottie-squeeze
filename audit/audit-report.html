Lottie Squeeze: Compression Engine Audit

Code review and measured benchmark of the browser-based Lottie compressor · 18 October 2026
Verdict: Not ready for professional release yet.
  • What works: the default settings give real, measurable savings (20–89% on the test files). On the vector-only test files, the output is visually indistinguishable from the original.
  • What's wrong: four bugs can silently damage files: a broken animation, lost transparency, garbage output at low precision, and broken mobile theming.
  • Effort to fix: all four are small, low-risk fixes in one file. After those fixes the tool moves to Ready with limitations.

No application code was changed during this audit. Every finding comes from reading the code and running the real engine.

How the testing was done

  • Harness: audit/harness.html loads the actual app in a hidden frame and calls its own optimizeLottie(), readDotLottie() and handleLottieFile(). It does not use a copy of the logic.
  • Visual check: each original and compressed animation is rendered with lottie-web 5.12.2 (canvas renderer), and every frame is compared pixel by pixel. Rendering the original against itself gives exactly 0 difference, so every difference reported comes from the compressor.
  • Score: "% pixels changed" is the share of pixels in the worst frame that differ by more than 16 out of 255 in any colour channel.
Coverage gap. No real After Effects or LottieFiles exports were available. The five test files are synthetic, generated to look like AE exports (numbers with 15–17 digits). Not covered: text layers, effects, 3D layers, audio, the SVG renderer (used by the preview), and Android/iOS players. Treat every number in this report as measured on these test files only.

B. Critical issues

B1. Hidden layers are deleted even when expressions use them Critical

  • Cause: removeHidden() (line 518) never checks whether the file has expressions.
  • Test: an expression reading thisComp.layer('Controller') lost its hidden controller layer. Result: 13.9% of pixels wrong, and the card no longer rotated.
  • Why it matters: hidden controller layers driven by expressions are common in professional rigs.

B2. "Auto" image mode destroys transparency Critical

  • Cause: hasAlpha() (line 503) only checks one pixel in four, so it misses transparency.
  • Test: a photo with a scattered transparent edge went from 9,600 transparent pixels to 0. The holes became solid dark green, saved as JPEG.
  • Same check elsewhere: it also decides whether a JPEG gets flattened onto white, and whether the WebP fallback keeps transparency.

B3. Low precision settings produce garbage, and the slider allows them Critical

Cause: the slider goes down to 0 (line 253), and cleanTree() rounds every number the same way.

Frame rate, frame times and time-remap values should never be rounded like positions are.

B4. Name stripping is on by default and silently breaks developer features Critical

  • It removes every layer name.
  • What breaks: colour and property changes done from code on Android, iOS and React Native (they find layers by name); any code that looks up layers by name; CSS that targets layer IDs or classes in lottie-web.
  • Why it's easy to miss: none of this shows up in the preview, so the option looks harmless. Expression detection only protects files that use expressions.

B5. Size figures that mislead Medium

  • Example animation: the "96.7% saved" compares against pretty-printed JSON (line 688), which was 4× bigger than minified JSON in the test files.
  • .lottie input: "before" is the zipped file size (line 753) while "after" is unzipped JSON. With images kept, a 210 KB .lottie becomes 280 KB of JSON, so the page shows about +33% instead of a saving.
  • No .lottie output: the result cannot be saved back as .lottie.
  • No gzipped baseline: only the gzipped size of the output is shown, not of the original.

B6. Re-compressing an already compressed file keeps degrading its images Medium

  • Three passes in a row raised the changed pixels from 6.1% → 7.8% → 9.0%.
  • How it happens: the "Optimize further" button on the video tab, or someone re-uploading their output.

B7. Wrong property count in shape groups after removing hidden shapes Low

  • 28 of 29 groups ended up with a property count (np) that no longer matches their contents.
  • lottie-web ignores it (no visual difference); other players are untested.

C. Missing capabilities

  1. Smarter rounding per property type: e.g. 2 decimals for positions and paths, 3 for colours and easing, never rounding times or frame rate.
  2. Keyframe optimization: turn an animated property whose keyframes are all identical into a static value; drop redundant middle keyframes; drop easing on the last keyframe; drop zero spatial tangents.
  3. Removing default values such as hd:false, bm:0, ddd:0, ao:0 (defaults need checking per player first).
  4. Merging duplicate images and precomps.
  5. Saving as .lottie: a zip with images as separate files, usually the smallest format for delivery.
  6. Removing dead layers: layers entirely outside the timeline, or at 0% opacity the whole time.
  7. Background processing (Web Worker), cancelling stale runs, and caching decoded images.
  8. A built-in "Verify" step that compares frames like the harness does and shows a quality score.
  9. Gzipped sizes before and after, since servers send files gzipped.

Compared with LottieFiles: their optimizer was not run, because that would mean uploading test files to their service, so no parity or comparison is claimed. Publicly, their tool is described as offering precision reduction, removing unused data and converting to .lottie. Of those, this tool lacks .lottie output and per-property rounding.

  • No visual change: minifying and removing metadata, names and unused assets. Removing hidden layers also, except in files with expressions (B1). Removing names does break developer features (B4).
  • Lossy: precision rounding and image re-encoding.
